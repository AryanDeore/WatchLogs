Message schema prototype — the Flush payload & Event objects

Question this answers (wayfinder ticket #2): what exactly does the Extension POST to the App on a Flush? Drive a mock viewing session with the domain-language buttons below and watch the exact JSON body that would go over the wire build up on the right. The goal is to feel whether this shape can represent every case — seeks, video changes in one tab, background audio, crash recovery — before it is written into the Extension. Everything here is throwaway; the pure buildFlush() module in the source is the only part meant to survive.

Event — type-specific fields

typeExtra fieldsMeaning
mediaFound—A media element with a resolvable id appeared. Starts the View.
play—Playback began / resumed.
pause—Playback paused (user, buffering stall, or tab throttle).
seekedfrom, to (number, sec)Position jumped. from is the pre-seek position.
ratechangerate (number)Playback speed changed. Watched time still accrues in wall-clock, not media time.
visible / hidden—Tab entered / left the foreground (visibilitychange).
pipEnter / pipLeave—Picture-in-Picture toggled. PiP still counts as Watched.
metadataChangechanged (object: field → new value)One or more View header fields resolved or changed. The View header also carries the new values.
sampleplaying (bool), visible (bool)5s heartbeat. Bounds data loss and lets the App detect a missed pause/hidden. pos is the sampled position.
ended—Media reached its natural end. The View may still receive more Events (a replay).
viewEndedreason (enum)nav | tab-closed | video-changed | crash-recovered. Last Event of the View. For crash-recovered, t/pos are the last known sample, not "now".

Open questions this prototype is here to settle

1. Time as epoch-ms int, not ISO string. Smaller, trivially comparable, and skew-correction is arithmetic. Logs lose readability. Prototype assumes epoch ms everywhere (t, sentAt, startedAt). OK?
2. Position in float seconds, not ms. Matches HTMLMediaElement.currentTime. Rounded to 3 decimals on the wire. OK?
3. Extension mints viewId / flushId (uuidv4). App never generates ids; it correlates on viewId and dedups Flushes on flushId. Alternative: App assigns ids on first sight and Acks them back. Prototype uses Extension-minted. OK?
4. Is open redundant? It equals "this batch has no viewEnded for the View." Keep as a convenience field, or drop it and make the App derive it? Prototype keeps it, flagged.
5. videoChange dropped as a standalone Event. A new video id in one tab = old View gets viewEnded reason video-changed, new View starts with previousViewId set. No separate videoChange event. Agree, or is an explicit event still wanted?
6. sample cadence = Flush cadence (5s). So a normal Flush carries ~1 sample per active View. Ticket #6 (Segment rules) may want finer (1s) samples to bound loss — that would decouple the two cadences. Leave at 5s for now?
7. Idempotency: Flush-level + Event seq. App stores seen flushIds and replays the Ack on a dup. Within a View, seq lets a re-send that overlaps a prior partial success dedup cleanly. Ack returns the highest seq accepted per View. Enough?
8. Ack shape. { flushId, accepted: true, views: [{ viewId, ackSeq }], serverTime }. On rejection: HTTP 4xx + { error }, no body-level partial failure. Fine, or does the App need per-View partial accept?
9. Metadata lives in two places. The View header always holds the latest known title/author/etc., and a metadataChange event records the moment it changed. Redundant-but-useful, or header-only?
10. background is not on the wire. The Extension reports raw facts (hidden, sample.visible=false); the App decides what is Background audio. Confirm the schema carries no derived/computed fields at all.
